## Question 2

````text
Round: ununemploy integrations — round 1
Question: What functional-programming approach should guide the implementation?
Description (Markdown source):
A functional core would calculate results from explicit inputs; a small outer layer would fetch pages and commit database writes. For example:

```ts
mergeObservation(previous, incoming)
transitionQueue(state, event, now, policy)
hashContent(normalizedContent)
```

These functions would return new values, avoid hidden database access and receive time explicitly when needed. Separate types would distinguish listing content, observation metadata and queue state. A functional effects library could formalize more of the surrounding asynchronous work, but introduces another dependency and conventions to learn. Pure functions still need correct business rules; the remaining questions establish those rules.
Recommendation: Use ordinary TypeScript with pure functions, readonly inputs and discriminated unions. Keep network and SQLite operations explicit at the boundary, and add a library only if a concrete problem warrants it.
Options: Plain TypeScript with a functional core / Evaluate a functional effects library before choosing / Compare approaches in a small prototype first
Selected: Plain TypeScript with a functional core
Notes:
````

## Question 3

```text
Round: ununemploy integrations — round 1
Question: Should this pass change the persisted queue representation?
Description (Markdown source):
The queue currently stores a full job document alongside the source observation and selected job content. That duplication contributes to the stale-metadata problem. We can first make both paths use one merge rule while keeping the tables, or move toward a queue containing only the job locator and retrieval state. The latter removes a second content owner but requires migration and recovery checks.

Saved jobs, manual edits, source IDs, checkpoints, counters and existing history must be preserved under either choice. The timestamp fix can stop future redundant versions without deleting old ones.
Recommendation: Keep the current tables for the first corrective pass. Establish one merge rule and explicit state transitions, then remove duplicate stored content only if it delivers a clear additional simplification.
Options: Keep existing tables in the first pass / Allow a targeted queue migration in this pass
Selected: Keep existing tables in the first pass

```

## Question 4

```text
Round: ununemploy integrations — round 1
Question: When a new listing card contradicts an older detail page, which metadata should the job show?
Description (Markdown source):
Example: yesterday's full page said Engineer and salary 100. Today's card for the same vacancy says Senior Engineer and salary 200, but its description is only an excerpt. The current queue keeps the old title and salary because it protects the entire full document.

This decision concerns explicit, usable values from the same source. Missing fields and placeholders are not evidence of a new value. Manual edits retain their established precedence.
Recommendation: Accept the newest explicit metadata while retaining the complete description and its original provenance. Make that a deterministic merge rule shared by collection and ingestion.
Options: Use newer explicit metadata; retain the full description / Keep detail-page metadata until the detail page is refreshed / Keep old values and prioritize a detail recheck when values conflict
Selected: Keep detail-page metadata until the detail page is refreshed
Notes:
```

## Question 5

```text
Round: ununemploy integrations — round 1
Question: How should fit assessment handle contradictory hiring-country evidence?
Description (Markdown source):
An office location and a hiring-country restriction describe different things and must stay separate. The audit's lost US restriction is unambiguously a bug. A harder case is a schema that restricts applicants to the US while the visible description explicitly says applicants worldwide are eligible.

We must retain both pieces of source evidence. This choice determines the assessment shown while the conflict is unresolved; it does not permit assuming citizenship or work authorization.
Recommendation: Mark hiring eligibility uncertain and explain the conflicting evidence. Avoid silently selecting whichever field happened to be parsed last.
Options: Keep both and mark eligibility uncertain / Apply the narrower explicit hiring restriction / Prefer explicit hiring statements in the visible description
Selected: Keep both and mark eligibility uncertain
Notes: whatever is the simplest and lightest. its fine to not be super accurate here.
```

## Question 6

```text
Round: ununemploy integrations — round 1
Question: What evidence should allow a previously closed vacancy to reopen?
Description (Markdown source):
Rediscovery should make a closed URL eligible for a bounded recheck; it should not itself declare the job open. We also need to distinguish a past HTTP 404 from an explicit employer expiry date. A matching page returning normally can overturn a temporary 404, while an expired posting may still have a readable page.

The existing expiry rules and saved-job history must survive the transition.
Recommendation: Allow a matching current detail page with no closure evidence to reverse a 404-based closure. Require explicit newer active evidence to supersede an employer expiry. Encode the closure reason so these cases cannot collapse into one boolean.
Options: Reopen according to the closure reason and current evidence / Require a newer publication or future expiry for every reopening / Keep previously closed jobs closed until I reopen them manually
Selected: Reopen according to the closure reason and current evidence
Notes: keep it simple here.
```
